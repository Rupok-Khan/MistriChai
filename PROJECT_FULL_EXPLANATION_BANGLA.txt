নোট
---
এই নথি তৈরি করা হয়েছে বর্তমান source code দেখে। client/server-এর নিজের লেখা source file-গুলো এখানে কভার করা হয়েছে। client/dist ও node_modules-এর ফাইল build output/third-party dependency; এগুলোর প্রতিটি generated/library line ব্যাখ্যা করা প্রজেক্ট বোঝার জন্য প্রাসঙ্গিক নয়। package-lock ফাইল dependency-এর exact version lock করে, business logic বহন করে না।

১. প্রজেক্টের উদ্দেশ্য
-----------------------
MistriChai একটি home-service booking platform। Customer প্রয়োজনীয় technician/service খুঁজে booking করে। Partner নিজের পরিচয়, NID, category ও কাজের সময় দিয়ে নিবন্ধন করে; Admin যাচাই করে অনুমোদন দিলে সে কাজ পায়। Admin booking assign, payment, refund, user, content, contact এবং partner wallet পরিচালনা করে।

প্রধান actor:
* CUSTOMER: account, subscription, verified partner search, booking, payment reference, chat, cancellation, review।
* PARTNER: NID verification, profile, availability, assigned order, accept/reject, work payment, chat, wallet ও withdrawal।
* ADMIN: login, dashboard, partner approve/reject, booking/payment/assignment/refund, customer/partner management, contact reply, service ও website content management।

২. System architecture ও data flow
------------------------------------
Browser (React + Vite) -> REST API (JSON/FormData + JWT) -> Express route -> middleware -> controller -> model -> MySQL। ছবি Multer দিয়ে গ্রহণ হয়ে Cloudinary অথবা local uploads-এ যায়। Frontend Vercel এবং backend Render-এ deploy করা যায়।

একটি সাধারণ request-এর ধাপ: React page form state নেয়; service function api wrapper-এ request পাঠায়; route endpoint middleware চালায়; auth middleware token যাচাই করে; role middleware অনুমতি পরীক্ষা করে; controller input ও business rule প্রয়োগ করে; model parameterized SQL চালায়; controller JSON response দেয়; page state refresh করে।

৭. Controller layer—business logic
------------------------------------
server/controllers/auth.controller.js: signup-এ duplicate email/mobile পরীক্ষা, bcrypt hash, users insert, customer_profiles/partner_profiles insert এবং token/session response দেয়। Partner signup-এ ছবি, NID, working time/category সংরক্ষণ হয় এবং verification PENDING থাকে। Login-এ bcrypt.compare; partner code/mobile/email দিয়ে user খোঁজা; inactive বা rejected policy check; access/refresh token তৈরি।
server/controllers/customer.controller.js: customer dashboard aggregate data, profile update, active subscription; plan (SIX_MONTHS/ONE_YEAR) ও unique transaction reference; approved partner filter; booking-এর customer ownership; payment reference; cancellation/change request; partner/customer chat; completed booking-এ 1-5 rating—এসব rule প্রয়োগ করে।
server/controllers/partner.controller.js: partner নিজের profile/availability update করে; কেবল assigned/নিজের booking দেখতে পারে; accept করলে status IN_PROGRESS/প্রাসঙ্গিক flow; rejection হলে change request তৈরি; work payment propose/confirm; attachment chat; কাজ complete হলে wallet credit এবং withdrawal validation চালায়।
server/controllers/admin.controller.js: admin-এর সবচেয়ে বড় orchestration layer। partner approve করলে code তৈরি/verification status বদলায়; reject করলে reason; booking assign করলে requested/assigned partner ও status; payment approve/refund status; cancellation/rejection review; work payment approve; wallet withdrawal pay; customer/partner update/delete; contact reply; site settings/service upload ও CRUD।
server/controllers/contact.controller.js: authenticated sender-এর user id/role সহ message insert/list; input ও ownership নিশ্চিত করে।
server/controllers/site.controller.js: public settings/services read এবং admin update-এর payload/file merge; malformed content normalize করে safe default রাখে।

৯. Database design (server/schema.sql)
--------------------------------------
users: central identity table। id PK, role ENUM, name/email/mobile unique identity, bcrypt password_hash, is_active।
customer_profiles: user_id UNIQUE FK; customer address আলাদা profile table হওয়ায় identity ও domain data আলাদা।
partner_profiles: user_id UNIQUE FK; partner_code, নাম, NID address/number/photos, district/thana/ward, category, working time, experience, social links, verification_status এবং availability_status। NID number unique।
customer_subscriptions: customer, plan, amount, start/expiry, ACTIVE/EXPIRED/CANCELLED status ও unique transaction_reference।
site_settings: section_key PK এবং LONGTEXT JSON; ফলে homepage/contact/about/services admin panel থেকে editable।
service_bookings: booking_code unique, customer, requested/assigned partner FK, category/problem/location/date/time, fee/estimated cash, status state machine, notes/rating/timestamps। requested partner পরে বদলালেও assigned relation আলাদা থাকে।
booking_messages: booking FK এবং sender/receiver FK; text অথবা attachment metadata। booking delete হলে message cascade delete।
booking_change_requests: requester, request_type, reason/proof, admin review status/note/audit timestamp।
payment_transactions: booking/payer/receiver nullable FK, BOOKING_FEE/SERVICE_CASH/REFUND/WITHDRAWAL, method, amount/status/reference।
work_payments: একটি booking-এর জন্য UNIQUE final job payment; customer/partner, amount, bKash id ও proposal/approval status।
partner_wallets: এক partner-এর এক wallet; current balance।
partner_payout_methods: partner-এর এক payout method; bKash/Nagad/Rocket/Bank details।
wallet_transactions: append-only ledger—CREDIT/DEBIT/WITHDRAW_REQUEST/WITHDRAW_PAID; booking ও payout snapshot রাখে।
contact_messages এবং contact_message_replies: support message ও admin reply; parent message delete হলে reply cascade।

Foreign key-তে customer/partner delete হলে profile/booking/payment-এর ক্ষেত্রে CASCADE বা SET NULL policy আছে। ENUM status ভুল value আটকায়; UNIQUE duplicate booking/mobile/reference আটকায়; DATETIME/audit field chronology দেয়।

১০. মূল business flow
----------------------
Registration -> bcrypt password -> login JWT -> customer active subscription -> approved partner search -> booking PAYMENT_PENDING -> admin payment approve -> assignment -> partner accept/in-progress -> work amount/payment approval -> COMPLETED -> wallet credit -> customer rating।
Customer cancellation, partner rejection বা partner change সরাসরি destructive update না করে booking_change_requests তৈরি করে; admin review-এর পর REFUND/CANCELLED/assignment পরিবর্তন হয়। এতে auditability থাকে।

Authentication flow: login-এ password hash compare; server signed JWT দেয়; client token রাখে এবং Authorization header পাঠায়; middleware verify করে। Customer/partner refresh cookie দিয়ে access token renew করতে পারে। Admin token আলাদা storage key ব্যবহার করে। Logout-এ client token ও server session/cookie clear হয়।

Payment flow: subscription payment এবং booking fee আলাদা concept; final work payment আলাদা work_payments; partner earning সরাসরি booking completion-এর পরে wallet CREDIT। withdrawal request pending থাকে; admin pay করলে reserve রেখে wallet debit এবং PAID ledger লেখা হয়।

১৬. Error, security ও quality notes
------------------------------------
Password কখনো plain text নয়; bcrypt hash। SQL parameterized। CORS allow-list। login ও submission rate limit। production-এ 500 response থেকে stack/error বাদ। upload size/type restriction। role এবং ownership check জরুরি—এক customer যেন অন্যের booking/chat না দেখতে পারে। Cloudinary credential env-এ থাকে; .env commit করা যাবে না। Render-এর ephemeral disk-এর কারণে production image-এর জন্য Cloudinary ব্যবহার করা উচিত।

১৭. Viva প্রশ্ন ও সংক্ষিপ্ত উত্তর
----------------------------------
১) MistriChai কী? — Customer, verified partner ও admin-কে যুক্ত করা home-service booking platform।
২) React কেন? — reusable component, state management ও SPA navigation।
৩) Express route/controller/model আলাদা কেন? — endpoint, business logic ও SQL আলাদা রেখে maintainability বাড়াতে।
৪) JWT কীভাবে কাজ করে? — server signed token দেয়; পরের request-এ middleware signature/expiry/role verify করে।
৫) bcrypt কেন? — password one-way salted hash করে; database leak হলেও plaintext পাওয়া যায় না।
৬) 401 ও 403 পার্থক্য? — 401 authentication ভুল/নেই; 403 পরিচয় আছে কিন্তু permission নেই।
৭) MySQL কেন? — booking, user, payment-এর relational foreign-key consistency প্রয়োজন।
৮) Foreign key কী? — দুই table-এর record relation ও referential integrity।
৯) customer_profiles আলাদা table কেন? — user identity ও customer-specific address আলাদা, 1:1 profile design।
১০) requested_partner ও assigned_partner আলাদা কেন? — customer-এর পছন্দ এবং admin-এর final assignment ভিন্ন হতে পারে।
১১) status ENUM-এর সুবিধা? — invalid status database-এ ঢুকতে দেয় না এবং workflow স্পষ্ট।
১২) Transaction wallet-এ কেন? — balance update ও ledger insert একসাথে সফল/ব্যর্থ করতে।
১৩) Multer কী? — multipart/form-data file parse ও validation middleware।
১৪) Cloudinary কেন? — persistent remote storage/CDN; Render local disk স্থায়ী নয়।
১৫) CORS কী? — কোন frontend origin API call করতে পারবে তার নিয়ন্ত্রণ।
১৬) parameterized query কীভাবে নিরাপদ? — user input SQL string-এর অংশ না হয়ে bound value হয়, injection কমে।
১৭) site_settings-এ JSON কেন? — homepage-এর পরিবর্তনশীল content schema migration ছাড়াই section-wise রাখা যায়।
১৮) soft delete service কেন? — পুরোনো service/key/reference রেখে inactive করা যায়; history নষ্ট হয় না।
১৯) booking_change_requests কেন? — cancellation/rejection-এর কারণ ও admin decision audit trail রাখে।
২০) wallet reserve কী? — partner পুরো balance তুলে না নিয়ে minimum 100 টাকা রেখে দেয়।
২১) refresh token কী? — access token expire হলে নতুন access token নেওয়ার mechanism।
২২) rate limiter কেন? — brute-force login ও spam submission কমাতে।
২৩) React Context কী? — অনেক component-এ prop drilling ছাড়াই global auth/preferences share করা।
২৪) FormData কখন? — file upload সহ multipart request-এ; সাধারণ data-তে JSON।
২৫) polling বনাম WebSocket? — polling নির্দিষ্ট সময় পর fetch; WebSocket server push করে, real-time ও scalable হতে পারে।
২৬) Vercel ও Render-এর ভূমিকা? — Vercel frontend, Render Node/Express backend host করে।
২৭) Admin partner approve করলে কী হয়? — verification APPROVED, partner code/assignment eligibility তৈরি হয়।
২৮) rating validation কেন? — শুধু নিজের completed booking-এ সীমিত 1-5 rating নিশ্চিত করতে।
২৯) cascade delete-এর ঝুঁকি কী? — parent delete-এ child data মুছে যায়; production-এ retention/audit policy বিবেচনা দরকার।
৩০) ভবিষ্যৎ উন্নয়ন কী? — real payment gateway, WebSocket, tests, audit log, Redis cache, migration tool ও fine-grained permission।

শেষ কথা
--------
কোনো feature পরিবর্তন করলে সংশ্লিষ্ট route -> controller -> model/schema -> frontend service -> page/component এই chain পরীক্ষা করতে হবে। Database status বা permission বদলালে customer, partner ও admin—তিনটি dashboard-এর state transition এবং security ownership test করা আবশ্যক।

১৮. Advanced Technical Implementation Notes
-------------------------------------------

১৮.১ Database schema evolution
------------------------------
শুধু schema.sql পরিবর্তন করলেই production database-এর পুরোনো table আপডেট হয় না। তাই server/config/schemaSync.js-এ idempotent migration-style check রাখা হয়েছে। Server startup-এ missing table, column এবং index তৈরি করা হয়। ফলে নতুন deployment-এ database manually recreate না করেও schema update করা যায়।

এই iteration-এ তিনটি গুরুত্বপূর্ণ database design যোগ হয়েছে:

১) idempotency_keys: একই user-এর একই request পুনরায় এলে একই entity ফেরত দেওয়ার জন্য। idempotency_key + scope composite unique key duplicate request আটকায়। Scope ব্যবহার করা হয়েছে যাতে দুই customer একই random key পাঠালেও তারা একে অপরের booking block না করে।

২) audit_logs: কে কোন business action করেছে তার history। actor user/role, action, entity type/id, before_json, after_json, request_id, IP এবং timestamp রাখা হয়। Debugging ও dispute resolution-এ current table value যথেষ্ট নয়; audit log পরিবর্তনের ইতিহাস দেয়।

৩) platform_commissions: final work payment-এর gross amount, 4% rate, commission amount এবং partner-এর net amount আলাদা করে সংরক্ষণ করে। Admin revenue wallet balance থেকে অনুমান না করে এই ledger table থেকে হিসাব করে।

১৮.২ Database index ও query performance
----------------------------------------
বড় table-এ full table scan হলে traffic বাড়ার সঙ্গে response time খারাপ হয়। Query pattern অনুযায়ী composite index দেওয়া হয়েছে:

* service_bookings(customer_user_id, status, booked_at): customer dashboard booking query।
* service_bookings(assigned_partner_user_id, status, assigned_at): partner order list।
* service_bookings(status, booked_at): admin status filter/recent booking।
* payment_transactions(booking_id, transaction_type, status): payment join/status validation।
* booking_messages(booking_id, created_at, id): chronological chat query।
* wallet_transactions(partner_user_id, transaction_type, status, created_at): wallet history ও pending withdrawal।
* booking_change_requests(status, created_at): admin pending request queue।

সব column-এ index দেওয়া হয়নি, কারণ প্রতিটি index write/update-এ অতিরিক্ত খরচ ও disk নেয়। WHERE, JOIN এবং ORDER BY-তে নিয়মিত ব্যবহৃত field-ই বেছে নেওয়া হয়েছে।

১৮.৩ Atomic booking ও payment transaction
------------------------------------------
Manual booking fee-সহ booking তৈরি করার সময় service_bookings এবং payment_transactions—দুইটি logical write হয়। প্রথমটি সফল কিন্তু দ্বিতীয়টি ব্যর্থ হলে payment ছাড়া PAYMENT_PENDING booking থেকে যেতে পারত। createBookingWithPayment() এই write-গুলো একই MySQL transaction-এ চালায়:

BEGIN → booking insert → booking code update → payment insert → idempotency key insert → COMMIT

যেকোনো exception হলে ROLLBACK হয়। finally block-এ connection release করা হয়, ফলে connection pool exhaustion কমে। Subscription customer-এর booking fee নেই, তাই payment insert হয় না; booking সরাসরি PENDING_ASSIGNMENT হয় এবং query-level payment status PAID হিসেবে প্রকাশ করা হয়।

১৮.৪ Idempotency ও duplicate request
-------------------------------------
Double-click, slow network retry অথবা mobile browser পুনরায় request পাঠালে একই booking দুইবার তৈরি হতে পারে। Frontend CustomerService.createBooking() একটি Idempotency-Key পাঠায়। Backend key-টি customer scope-এর সঙ্গে database-এ রাখে। Key আগে থাকলে নতুন insert না করে আগের booking id ফেরত দেয়।

এটি শুধু button disable-এর উপর নির্ভর করে না; database unique constraint এবং backend lookup authoritative protection। bKash transaction reference-এর উপরও unique constraint আছে, ফলে একই payment reference দ্বিতীয় booking-এ ব্যবহার করা যায় না।

১৮.৫ Wallet ও 4% commission settlement
----------------------------------------
Final work amount gross হিসেবে G এবং platform rate R = 0.04 হলে:

commission = round(G × R, 2)
partner_net = round(G - commission, 2)

উদাহরণ: G = ৳১০০০ হলে commission = ৳৪০ এবং partner_net = ৳৯৬০। Wallet.creditCompletedWork() একই transaction-এ duplicate CREDIT পরীক্ষা, partner wallet-এ net balance যোগ, wallet ledger insert এবং platform_commissions insert করে। সব সফল হলে COMMIT হয়।

Completion endpoint পুনরায় call হলেও একই partner ও booking-এর CREDIT আগে আছে কি না FOR UPDATE দিয়ে পরীক্ষা হয়। Withdrawal-এর সময় withdrawal row এবং wallet row lock করা হয়; দুইজন admin একই withdrawal pay করতে চাইলেও দ্বিতীয় request processed status দেখে থেমে যায়। Wallet reserve ৳১০০-এর নিচে নামতে দেওয়া হয় না।

১৮.৬ Subscription-এর server authority
--------------------------------------
Plan price client-side display হলেও final authority backend Subscription.PLANS:

ONE_MONTH = ১ মাস, ৳৩০
SIX_MONTHS = ৬ মাস, ৳১৪৯
ONE_YEAR = ১২ মাস, ৳২৫০

Client amount edit করলেও server plan_code দিয়ে নিজেই amount/months নির্ধারণ করে। Active subscription query expired record-কে EXPIRED করে এবং expires_at > NOW() record নেয়। Subscription booking-এ booking_fee শূন্য; admin approval কেবল PAYMENT_PENDING booking-এর জন্য প্রযোজ্য।

১৮.৭ Backend request lifecycle ও error strategy
------------------------------------------------
Security middleware request id তৈরি করে; এটি response header এবং audit log-এ ব্যবহার করা যায়। Route authentication/role check-এর পরে controller চলে। Controller validation, ownership, status transition, model call এবং safe response পরিচালনা করে। Model SQL query ও database result পরিচালনা করে।

Status-এর অর্থ: 400 invalid input/workflow, 401 invalid login/token, 403 permission নেই, 404 resource নেই/অন্যের resource, 409 duplicate বা state conflict, 429 rate limit, 500 unexpected server/database error। Production-এ 500 response থেকে stack সরানো হলেও request_id রাখা হয়।

১৮.৮ Ownership ও authorization
------------------------------
JWT valid হলেই booking access দেওয়া হয় না। Customer controller customer_user_id-এর সঙ্গে req.user.id মিলায়; Partner controller assigned_partner_user_id-এর সঙ্গে নিজের id মিলায়; Admin আলাদা middleware দিয়ে protected। Assignment-এ payment_status PAID, valid partner এবং PENDING_ASSIGNMENT/WAITING_FOR_PARTNER—সব condition backend-এ পরীক্ষা হয়। শুধু frontend button disabled নিরাপত্তা নয়।

১৮.৯ Frontend state ও data fetching
------------------------------------
Dashboard load function Promise.all দিয়ে independent API call parallel চালায়। loading শুরুতে true, success-এ state update, failure-এ error, finally-তে loading false। `work-payments` response-এ `data: []` error নয়; এর অর্থ কোনো final payment request এখনো নেই।

Booking page-এ selected partner, bookingStep, form state এবং subscription state আলাদা রাখা হয়েছে। Step 1 details, Step 2 schedule, Step 3 payment/review—বড় form-এর cognitive load কমায়। `required` browser validation দেয় এবং CSS `:has()` selector label-এর পাশে automatic লাল asterisk দেখায়; backend validation আলাদা থাকে, কারণ browser validation bypass করা যায়।

API wrapper JSON ও FormData আলাদা handle করে। File upload-এ Content-Type manually set করা হয় না; browser multipart boundary বসায়। 401 হলে customer/partner refresh flow চেষ্টা হয়; admin token-এর ক্ষেত্রে session expired event দিয়ে login-এ পাঠানো হয়।

১৮.১০ CORS custom header debugging
-----------------------------------
Idempotency-Key custom request header হওয়ায় browser cross-origin POST-এর আগে OPTIONS preflight পাঠায়। Backend CORS allowedHeaders-এ header না থাকলে browser POST পাঠাতে দেয় না এবং “Request header field idempotency-key is not allowed” দেখায়। তাই app.js-এ Idempotency-Key allow করা হয়েছে।

Network tab developer-only diagnostic data; authenticated response সম্পূর্ণ গোপন করা যায় না। Sensitive data কমানোর নিয়ম হলো প্রয়োজনীয় field মাত্র পাঠানো, password/secret না পাঠানো এবং server-side authorization রাখা।

১৮.১১ বর্তমান limitation ও পরের production step
-------------------------------------------------
বর্তমান payment manual bKash reference-based; real gateway webhook এখনো নেই। Commission completion-এর পরে wallet-এ settle হয়। পরের ধাপে payment gateway/signed webhook, commission refund policy, private NID storage, automated tests, audit viewer, centralized monitoring, backup/restore drill, Redis/WebSocket notification এবং versioned migration যোগ করা যায়।
